# 型安全なヘッドレスCMS・フォーム受付基盤 要件定義書

文書状態：改訂案。初期版の要求・要件を定義する。

## 1. 目的

開発者がコードで定義したスキーマを使い、コンテンツ管理とフォーム受付を行う。開発者は表示アプリを自由に実装し、運営者はCMSで日常の管理を行う。

標準的なコーポレートサイトを、フォーム専用サービスの追加契約なしで運用できることを目指す。セルフホスティングを初期の提供形態とし、将来のSaaS提供を考慮する。

本書は利用者の体験、必要な能力、保証範囲、運用上の条件を定義する。画面構成、API、データ構造、技術選定、処理方式は設計で決定する。利用者に見える挙動と達成条件は、本書に従う。

複数の観点を含む節は、次の二つに分けて記述する。

| 区分 | 記述する内容 |
|---|---|
| 状態と規則 | CMSが保持する対象の状態、状態が変わる条件、操作の経路によらず常に守る規則 |
| 操作と表示 | 利用者が行える操作、操作に必要な確認、利用者が確認できる情報 |

本書が定める状態は、利用者が確認でき、操作の可否や取得結果を左右するものに限る。処理の進行を管理する内部の状態は設計で定める。

本書では、次の用語を区別して使う。

| 用語 | 意味 | 例 |
|---|---|---|
| キー | モデル・フォーム・項目・選択肢・ブロックの種類をスキーマ上で識別する名前。開発者がコードで定義する | `news`、`title` |
| 表示名称 | 編集画面に表示する名前。変更してもデータや設定に影響しない | ニュース、タイトル |
| コンテンツID | コンテンツ一件ごとにCMSが割り当てる、変わらないID | ─ |
| 一意な値 | 同じモデル内で一意にする制約を持つ項目の値。URLの一部などに使う | `company-news-2026` |
| 問い合わせ対象 | フォームのコンテンツ参照の項目で、送信者が指定したコンテンツ | 問い合わせるサービス |
| 移行定義 | スキーマの差分から生成する、既存データの扱いを伴う変更の記録。コンテンツの構造の変更と、差分だけでは決まらない開発者の判断を記録する。コードで管理し、順に適用する | ─ |
| 直接反映 | 移行定義を作らずに、スキーマの構造を反映すること。移行定義の適用記録に残さない | ─ |
| 初期構成 | 設置のデータが空の状態で起動したときにだけ読み込む、ワークスペース・所有者・トークン・運用設定の宣言。読み込んだ後は管理画面の設定を正本とする | ─ |
| 非推奨 | 段階的な変更で削除予定の対象に付けるスキーマの属性。値、取得結果、入力検証は変えず、型で示し、編集画面では変更できなくする | ─ |
| 公開内容 | コンテンツのうち、公開取得で配信している内容 | ─ |
| 下書き | コンテンツのうち、公開していない編集中の内容。未公開のコンテンツの内容と、公開中のコンテンツに対する未公開の変更の両方を指す | ─ |
| 最新の内容 | 下書きがあれば下書き、なければ公開内容。プレビュー取得と管理画面で使う | ─ |
| 値の書き換え | コンテンツの指定した項目の値を、公開内容と下書きのそれぞれを選んで書き換える操作。公開・公開取り消しとして扱わない | ─ |
| トークン | アプリがCMSへの要求で示す認可の情報。ワークスペースが発行し、許可と種類を持つ | ─ |

## 2. 利用者と責務

| 利用者 | 主な目的 |
|---|---|
| 開発者 | コンテンツ・フォームをコードで定義し、表示アプリを開発する |
| 所有者・管理者 | ワークスペース、メンバー、権限、通知先・通知メール、運用方針を管理する |
| 編集者 | コンテンツとメディアを作成・編集・公開する |
| 閲覧者 | 許可された管理対象を確認する |
| サイト訪問者 | 公開コンテンツを閲覧し、フォームを送信する |
| ホスティング運営者 | 導入、更新、状態確認、バックアップ、復旧、ワークスペースの作成と利用終了を行う |

一人が複数の役割を担える。ワークスペースの管理権限と、設置全体の運用権限を区別する。

CMSは、スキーマの受け入れ、入力検証、コンテンツ管理、フォーム受付、通知、アクセス制御を担う。

利用者は、スキーマの定義、リポジトリ構成、複数アプリでの共有、表示アプリの実装・配信、アプリ独自の業務上の権限、アプリに持たせるトークンの保管を管理する。表示アプリは、プレビューで取得した下書きや、下書きを含むビルドの成果物を誰に見せるかを制御する。

開発者は、スキーマ変更に対応する表示アプリの準備と切り替え、移行を適用する時期の決定、データを失い得る操作を含む移行の前のバックアップの確認、移行定義で扱わないデータの変換、開発・検証に使う環境とデータの用意を行う。ホスティング運営者は、設置環境の容量確保、バックアップの実行・保護、復旧手順の検証を行う。CMSは、各作業の前提条件と確認できる結果を示す。

## 3. 開発体験

### 3.1 スキーマの定義と反映

#### 状態と規則

- コンテンツとフォームのスキーマは、利用者側のコードを正本とする。通知メールの定義はスキーマに含めず、8.3に従って運用設定として管理画面で管理する。
- 反映はワークスペースのスキーマ全体を単位とする。一部のモデル・フォームだけを反映しない。複数のアプリで一つのワークスペースを使う場合は、一つのスキーマの定義を共有する。
- コードで管理する範囲は、モデル・フォーム・項目・選択肢・ブロックの種類のキー、表示名称・順序、型、制約、説明・入力例、初期値、参照を許可するモデル、一覧表示・検索・問い合わせ対象の表示に使う項目、画像の派生形式、6.4の非推奨、5.3のモデルごとのプレビュー先の経路、6.1の移行定義とする。
- 管理画面で管理する運用設定は、メンバー・権限、アプリのトークン、通知先、8.3の通知メールの定義、送信接続設定、表示アプリへの通知設定、プレビュー先の表示アプリのURL、フォームの受付状態、回答の保持方針、コンテンツの保持方針とする。運用設定をスキーマの再反映で上書きしない。
- 運用設定に含む認証情報などの秘密情報は、登録後に値を表示せず、9.2に従って保護する。招待やアクセス回復に使う設置全体のメール送信は、ホスティング運営者が設置の設定として管理し、ワークスペースの送信接続設定と区別する。
- 運用設定はモデル・フォームに紐付ける。表示名称の変更と、移行定義によるモデルのキーの変更で設定を失わせず、別の対象へ引き継がない。
- モデル、フォーム、項目、選択肢、ブロックの種類のキーと、編集画面に表示する名称を区別する。名称の変更だけで別の対象として扱わない。
- 表示名称の変更では、キーと保存済みの値を維持し、値の移行を必要としない。コンテンツの構造のキーの変更は、6.2の移行定義で明示的に行い、データと運用設定を引き継ぐ。フォームとその項目のキーの変更は、6.5に従って削除と追加として扱う。
- 変更前のキーを使う取得・送信は、存在しない対象への要求として3.2に従って扱う。
- 削除したキーと変更前のキーの再利用は6.2に従う。
- 新規フォームは、10.1の初期構成で受付中と宣言した場合を除き、受付停止状態で作成する。
- 不正なスキーマの反映は拒否し、現行スキーマ、データ、運用設定を変更しない。構造の変更を伴う反映は6章に従う。

#### 操作と表示

- スキーマをCMSに反映すると、定義に対応した編集・受付機能を利用できる。管理画面で同じ構造を二重に定義する必要はない。
- 項目の説明、入力例、制約を定義でき、編集者が参照できる。
- フォームの受付は、通知先・送信接続設定、保持方針を確認してから有効にする。通知定義の参照の不整合は受付を妨げず、8.3に従って扱う。定義の変更時の受付は6.5に従う。
- 反映済みの内容、反映結果、反映できない理由を確認できる。
- スキーマ自体の不整合を、CMSに接続せずに開発環境で検出し、該当する定義と理由を示す。キーの重複、存在しないモデル・項目への参照定義、型に適用できない制約、初期値の型不適合、表示・検索用項目の不適合、必須の項目への非推奨の指定を検証する。CMSは反映時にも同じ検証を行う。反映で生じる通知定義の参照の不整合は、6.5に従って示す。
- スキーマを変更すると、CMSへ反映する前から、開発環境で変更後の型を使える。型を得るためにCMSへ接続する必要はない。
- スキーマ自体の不整合と、移行の適用で既存データが満たさない条件を区別して示す。
- 同時にスキーマを更新した場合、他の変更を気付かず上書きしない。
- リポジトリ構成やスキーマの管理主体をCMSが指定しない。
- 開発者は、CMSを手元に設置し、スキーマと移行定義を反映して、編集画面、型、取得、フォーム受付を試せる。手元の設置は運用中の設置と同じ機能を持ち、CMSは設置やワークスペースの用途によって機能を出し分けない。
- CMSは、データの初期化機能を提供しない。データを作り直す場合は、設置のデータの保存先を空にして起動し直す。空の状態での起動では10.1の初期構成を読み込み、ワークスペース、所有者、トークン、運用設定を同じ状態から用意する。
- 起動し直した後のデータ投入は、開発者の環境から9.3のコンテンツ管理の許可を持つトークンで行う。CMS内で利用者のコードを実行しない。投入するデータは開発者が用意する。
- スキーマの構造を直接反映できる。直接反映は9.3のスキーマ反映の許可で行う。既存データを保てない変更は、失われる値・項目・コンテンツを示し、開発者の確認を得てから反映する。直接反映した構造と移行定義の関係は6.1に従う。
- どのワークスペースへ直接反映するかは、開発者がスキーマ反映の許可を持つトークンの管理で制御する。CMSは、ワークスペースが運用中かどうかを判断しない。
- CMSは、開発・検証に使うコンテンツを用意するための操作を、9.3のコンテンツ管理の許可として提供する。運用中のデータに対する移行の結果は、6.1の適用の事前確認で確認できる。運用中の設置で検証に使うワークスペースは、通常のワークスペースとして扱う。

### 3.2 型とアプリ連携

- コンテンツの取得結果、フォームの送信内容、項目ごとの入力エラーを型付きで扱える。フォームの受付結果は、受付完了と、理由付きの受付失敗を識別できる。受付結果は8.2に従う。
- プレビュー取得で返す内容は、5.3に従い型を満たさない入力エラーのないものに限り、公開コンテンツと同じ型で扱える。
- アプリ側の型とCMS側の入力検証は、同じスキーマに基づく。
- 型を共有するために、同じ構造を手作業で重複定義する必要はない。
- 取得結果とフォーム送信は、現行スキーマに従う。
- アプリは、取得・送信の要求に、コードが前提とするスキーマの6.1の識別子を、スキーマ全体またはモデル・フォームごとに添えられる。CMSは、添えられた識別子ごとに、現行スキーマの識別子と一致するかを応答で示す。一致しないことを理由に要求を拒否しない。アプリは、識別子が一致しない応答を取得・送信の失敗として扱うよう選べる。
- アプリのコードが前提とするスキーマと現行スキーマの食い違いは、開発者が6.1の適用状況と、識別子の一致を示す応答で確認する。
- 存在しないモデル・フォーム・項目を指定した取得・送信は、対象のキーを示すエラーとして扱う。
- アプリとスキーマの切り替えは6.4に従う。
- Next.jsやReactと連携しやすく、他の表示技術からも利用できる。
- 初期設定後、通常の取得・送信のたびに接続や認証の定型処理を記述する必要はない。
- 認証処理を簡略化しても、非公開データへの認可を省略しない。
- SSG、SSR、SPA、スクリプトの各実行環境から、9.3のトークンで接続できる。実行環境ごとの代表的な使い方は次のとおり。

| 実行環境 | トークンの種類 | 主な許可 |
|---|---|---|
| SSG（ビルド時） | サーバー用 | 公開取得。下書きを確認するビルドではプレビュー取得 |
| SSR・サーバー側の処理 | サーバー用 | 公開取得、プレビュー取得、フォーム送信 |
| ブラウザ（SPAなど） | ブラウザ用 | 公開取得、フォーム送信 |
| スクリプト（開発者の手元など） | サーバー用 | スキーマ反映、コンテンツ管理 |

- ブラウザから直接、公開取得とフォーム送信を型付きで呼び出せる。サーバー用トークンをブラウザへ渡す構成を必要としない。
- フォームの表示、コンテンツの表示、アプリ固有の権限判定は表示アプリで制御する。

### 3.3 コンテンツの取得

- コンテンツの取得には、公開取得とプレビュー取得がある。公開取得は4.2の公開内容を、プレビュー取得は最新の内容を返す。どちらも9.3の許可を持つトークンで行う。返せない下書きの扱いは5.3に従う。
- 公開取得とプレビュー取得を区別できる。取得結果の型、単件・一覧の取得方法、絞り込み、並び替えは両者で共通とし、条件は返す内容の値に適用する。
- コンテンツを、コンテンツIDまたはスキーマで定義した一意な値で取得できる。単一モデルのコンテンツは、IDや一意な値を指定せずに取得できる。
- コンテンツの一覧を、項目の値で絞り込み、並び替え、件数を区切って取得できる。条件に該当する総件数も取得できる。
- 初期版の絞り込みは、モデル直下のテキスト・数値・真偽値・日付・日時・単一選択の完全一致、数値・日付・日時の範囲、複数選択の指定値の包含、コンテンツ参照のコンテンツIDによる一致を扱う。複数の条件をすべて満たす絞り込みができる。
- モデル直下のテキスト・数値・日付・日時・単一選択の項目と、CMSが管理する作成日時・更新日時で、昇順・降順に並び替えられる。CMSが管理する日時は4.2に従う。
- 公開日や掲載順など、表示アプリが意味を持たせる日時や順序は、スキーマの項目として定義して並び替えに使う。CMSは特定の項目を公開日として特別に扱わない。
- 未設定値の扱い、文字列の比較規則、日時の基準を開発者に示す。本文の全文検索、参照先の項目や入れ子内部による絞り込み、任意の論理式による検索は初期版に含めない。
- 一覧では、同じ並び替え条件で値が同じ場合にも順序を決められる。
- 一覧の途中で内容が変化する場合の重複・欠落の可能性を開発者が確認できる。複数回の取得をまたぐ固定された一覧の保証は初期版に含めない。
- 公開取得は、下書きの内容や存在を明かさない。未公開のコンテンツの存在と、公開中のコンテンツに下書きがあるかどうかも明かさない。
- 参照先の取得範囲と、取得件数・参照の深さの制限を確認できる。循環参照によって取得処理が終わらなくならない。

## 4. コンテンツと編集体験

### 4.1 管理する構造

- 記事などの複数件を持つモデルと、サイト設定などの単一の情報を扱える。
- テキスト、数値、真偽値、日付、日時、単一選択、複数選択、リッチテキストを扱える。テキストには、一行と複数行の入力を指定できる。
- 日付はタイムゾーンを持たない暦日とし、日時は時点として扱う。
- メディア、別のコンテンツへの参照、項目のまとまり、繰り返しを扱える。
- スキーマで許可した種類のブロックを組み合わせられる。
- 必須条件、初期値、編集者向けの説明と、次の標準の制約を設定できる。文字数、数値・日付・日時の範囲、テキストの書式、選択数、繰り返し・ブロック・参照先の件数。テキストの書式は、メールアドレス・URLの形式と、開発者が定義するパターンとする。利用者独自の検証関数をCMS内で実行しない。
- 日付・日時の初期値には、固定の値のほかに、作成時点の日付・日時を指定できる。
- URLの一部などに使う文字列の項目に、同じワークスペースの同じモデル内で一意にする制約を設定できる。この制約を持つ項目の値を一意な値と呼ぶ。一意性の規則は4.2に従う。
- 一意な値の変更を表示アプリへ伝えられる。URL設計と旧URLからの転送は表示アプリが担う。
- 編集上のラベルや表示順の変更と、保存する内容の構造変更を区別できる。

### 4.2 コンテンツの状態

一件のコンテンツは、変わらないコンテンツIDと、公開内容・下書きをそれぞれ最大一つ持ち、少なくとも一方を持つ。下書きはコンテンツごとに一つとし、編集者の間で共有する。過去の内容は7.1に従って履歴として保持する。

| 内容 | 意味 |
|---|---|
| 公開内容 | 公開取得で配信する内容。公開時の検証を満たす |
| 下書き | 公開していない編集中の内容。入力エラーを残したまま保存できる |
| 最新の内容 | 下書きがあれば下書き、なければ公開内容。編集、プレビュー取得、管理画面での表示・検索に使う |

公開状態は、公開内容の有無で決まる。下書きの有無は公開状態と独立して確認できる。

| 公開状態 | 公開内容 | 下書き |
|---|---|---|
| 未公開 | なし | あり |
| 公開中 | あり | なし、またはあり |

- コンテンツは、通常の管理対象またはごみ箱のいずれかにある。ごみ箱のコンテンツは未公開とする。
- 新規コンテンツは未公開として作成する。
- 下書きの入力エラーには、必須項目の欠落と、値の範囲・文字数・書式・選択肢・参照先などの検証エラーを含む。移行で制約を強めた結果の違反も含む。
- 編集で入力する値は、現行スキーマの値の種類・構造に従う。
- 編集は最新の内容から始め、保存すると下書きになる。公開内容と配信は、公開、公開取り消し、6.3の移行、値の書き換えでだけ変わる。
- 公開は、下書きを公開内容にして下書きをなくす。置き換え前の公開内容は履歴に残す。入力エラーを解消し、公開時の検証を満たすまで公開しない。下書きを持たないコンテンツは公開の対象にならない。
- 公開中のコンテンツは、下書きを破棄できる。破棄した下書きは履歴に残す。
- 公開を取り消すと、公開内容をなくし、最新の内容を下書きとして残す。下書きがあった場合は、公開内容を履歴に残す。
- 公開中のコンテンツのごみ箱への移動と完全削除は、公開取り消しを含む操作として扱う。
- 値の書き換えは、9.3のコンテンツ管理の許可を持つトークンで行う。指定した項目の値だけを変え、ほかの項目と、書き換え先に選ばなかった公開内容・下書きを変えない。下書きを公開せず、新たな下書きを作らない。下書きの書き換えは、下書きを持つコンテンツにだけ行う。ごみ箱のコンテンツも、ごみ箱に置いたまま下書きを書き換えられる。
- 公開内容の値の書き換えは、書き換え後の公開内容が公開時の検証を満たす場合に限り行い、書き換え前の公開内容を履歴に残す。下書きの値の書き換えは、入力エラーを残してよい。
- 値の書き換えは、読み取った後に他の操作で変わった内容を、気付かず上書きしない。
- ごみ箱のコンテンツは、移動時点の下書きと履歴を保持し、公開取得、プレビュー取得、通常の編集の対象にしない。ごみ箱のコンテンツも6.3の移行と値の書き換えの対象とし、復元時は未公開として戻す。復元だけでは公開しない。
- 一意な値は、公開内容の間で重複させない。一意性は公開時に確認し、同時操作でも保つ。下書き・ごみ箱・履歴の値は予約しない。
- 下書きの保存時にも、他のコンテンツの公開内容との重複を示す。
- CMSが管理する日時は、作成日時と、公開内容・下書きそれぞれの更新日時とする。公開内容の更新日時は公開または値の書き換えで公開内容を最後に変えた日時、下書きの更新日時は保存または値の書き換えで下書きを最後に変えた日時とする。取得では返す内容の更新日時を返す。下書きの保存と破棄で、公開取得に返す日時を変えない。
- アクセス制御は下書きの保存と破棄、値の書き換えにも適用する。

### 4.3 編集

- 定義した項目に対応する編集画面を利用できる。標準の項目ごとに独自の編集画面を実装する必要はない。
- 一覧、検索、絞り込みから対象を見つけ、新規作成、複製、編集、下書きの破棄、削除ができる。管理画面の一覧・検索・複製は最新の内容を使い、公開状態と下書きの有無を示す。削除はごみ箱への移動とし、完全削除は7.2に従う。
- 公開中のコンテンツを削除・完全削除する場合は、公開取り消しを含むことを示し、削除権限に加えて公開権限と5.2の参照条件を必要とする。
- 複製時は一意な項目を未設定にし、必要な入力を示す。
- 管理画面のコンテンツ検索は、コンテンツIDと、スキーマで指定する一覧表示用のテキスト項目を対象とする。コンテンツIDの完全一致とテキストの部分一致で検索でき、3.3の絞り込み・並び替えを利用できる。
- 公開状態、下書きの有無、下書きの入力エラーの有無で対象を絞り込める。ごみ箱の内容を通常の管理対象と区別して確認できる。
- コンテンツ参照の入力では、参照を許可したモデルのコンテンツを一覧表示用の項目で検索して選べる。候補ごとに公開状態と下書きの有無を示す。
- WYSIWYGで本文を編集できる。初期版は、段落、見出し、太字、斜体、箇条書き、番号付きリスト、引用、リンク、画像を扱う。
- 本文中の画像もメディアとして管理する。画像の代替テキストを設定できる。
- 本文の構造を表示アプリが解釈して描画できる。許可していない要素や危険な内容を取り込まず、入力の削除・変更が必要な場合は保存前に示す。
- 本文のリンクは、外部のURLと、同じワークスペースのコンテンツへのリンクを区別する。コンテンツへのリンクはコンテンツ参照として扱い、5.2の公開と削除の規則を適用する。表示アプリは、参照先のモデル、コンテンツID、一意な値からURLを組み立てる。
- 繰り返し項目や許可されたブロックを追加・削除・並べ替えできる。
- 入力の誤りや不足を、対象の項目と修正理由から理解できる。
- 未入力の必須項目や値の検証エラーがあっても、下書きを保存できる。エラー箇所を示し、解消するまで公開しない。
- 保存できない入力は、理由を示し、修正するまで編集画面に保持する。保存前の入力をCMSに保持することは求めない。
- 未保存の入力がある状態で編集画面を離れる場合は確認する。セッションの期限切れや通信断で保存できなかった入力は、再ログイン・再接続の後に保存し直せる。
- 公開中のコンテンツを編集するときは、保存しても配信が変わらないことを示す。下書きがある場合は、公開内容との差分を確認できる。
- 下書きの破棄は、破棄する変更を示して確認する。
- 保存状況を確認できる。
- 他の人による変更を、気付かず上書きしない。同じコンテンツを他のメンバーが編集していることを編集画面で確認できる。
- 保存が他の人の変更と競合した場合は、自分の入力を失わずに、他の人の変更との差分を確認し、取り込み直して保存できる。
- 非推奨の対象の表示と編集は6.4に従う。
- 編集者がページの色、装飾、自由な配置を決める機能は提供範囲に含めない。

### 4.4 メディア

#### 状態と規則

- メディアは非公開または公開のいずれかとする。登録したメディアは非公開とする。
- 非公開のメディアが、公開済みのメディアと同じ扱いで意図せず閲覧可能にならない。
- コンテンツの公開、移行、公開内容の値の書き換えに伴って新たに公開するメディアは、その操作の確定に合わせて公開する。操作が失敗・中止した場合は非公開を維持し、メディアだけを先に公開しない。下書きの保存、下書きの値の書き換え、プレビューだけでメディアを公開しない。
- 公開内容での使用箇所があるメディアは非公開化できない。
- 公開使用がなくなっても、メディアの公開を自動で取り消さない。
- 非公開化後はCMSが管理する配信で新しい取得を拒否する。外部で保存・複製された内容は回収できない。
- メディアの実体は登録後に変更しない。同じメディアの配信内容は変わらず、表示アプリや配信経路で長くキャッシュできる。実体を差し替える場合は新しいメディアとして登録し、使用箇所の付け替えはコンテンツの編集と公開、または値の書き換えで行う。
- 登録時に、メディアの形式、容量、画像の幅・高さを記録する。対応形式と容量の上限を満たさないファイルは登録を拒否する。
- 代替テキストやキャプションなど表示に使う説明は、メディアの使用箇所ごとに使用コンテンツの内容として持つ。メディア側の説明を変更しても、既存の使用箇所や公開表示を書き換えない。管理用の名称・検索情報の変更は公開表示に使わない。
- メディアの削除は完全削除とし、ごみ箱を設けない。コンテンツの公開内容・下書き、保持対象の履歴、ごみ箱のコンテンツのいずれかから使われているメディアは削除できない。
- 開発者は、画像の派生形式をスキーマで定義できる。派生形式は、大きさ、画像形式、圧縮の品質などの組とし、キーで識別する。
- CMSは元の画像を保持し、定義した派生形式を元の画像から生成して配信する。元の画像を変換結果で置き換えない。
- 取得結果では、元の画像と各派生形式の配信先、画像形式、幅、高さを型付きで扱える。
- 派生形式は元のメディアの公開状態に従い、元のメディアと同時に公開・非公開化・削除する。派生形式だけを先に公開しない。
- 派生形式の定義を追加・変更した場合は、登録済みの画像にも適用する。変更前の定義で生成した派生形式は、新しい派生形式を配信できるまで配信を続ける。
- 生成が終わっていない、または失敗した派生形式を、生成済みとして返さない。

#### 操作と表示

- メディアを登録し、登録済みのものを検索・選択・再利用できる。
- 画像の項目と本文へのファイルのドロップ・貼り付けで、メディアを登録して挿入できる。
- 登録を拒否した場合は、理由と対応形式・容量の上限を示す。
- 画像の代替テキストなど、利用に必要な説明を管理できる。共有するメディアの説明を、各使用箇所の説明に利用できる。
- 使用箇所の説明はコンテンツの編集で更新し、公開して反映する。
- 実体を差し替える場合は、新しいメディアを登録し、元のメディアの使用箇所を一覧して、各コンテンツの下書きで付け替えられる。
- 派生形式の生成状況と失敗を確認できる。
- 使用箇所と削除による影響を確認できる。削除できない場合は、使用箇所と7.2の解消方法を示す。
- コンテンツの公開時は、本文内と参照先を含む使用メディアの公開範囲を確認して公開する。
- コンテンツの公開に伴うメディア公開には、その操作を行える権限を必要とする。
- 権限を持つ利用者が、公開使用のないメディアを非公開化できる。

## 5. 公開とプレビュー

### 5.1 公開

公開に関わる状態は4.2に従う。

- 公開時に必要な検証を行い、問題を解消してから公開できる。
- 複数コンテンツを一括公開できる。すべての対象の検証と必要な権限の確認を終えてから確定し、一部だけを公開しない。
- 公開操作では、利用者が確認した内容を公開する。同時に変更された内容を気付かず公開したり失わせたりしない。
- 公開を取り消しても内容を失わず、下書きとして編集を続けられる。
- 下書きは、公開するまで公開取得に混ざらない。

### 5.2 参照先の公開と削除

- 公開コンテンツからのコンテンツ参照は、同じワークスペース内で、公開操作の確定後に公開済みとなるコンテンツに限る。公開内容を持たず、公開対象にも含まれない参照先は公開検証でエラーにする。
- 同じ操作で公開する対象間の参照と自己参照を許容する。互いを必須参照するコンテンツは一括公開できる。対象外の参照先には現在の公開内容を使う。
- 公開コンテンツは、参照先の現在の公開内容を参照する。参照先を再公開すると、CMSからの新しい取得では参照元の再公開なしに更新内容を取得できる。
- 参照先の再公開と、任意の参照だけで参照されている参照先の公開取り消しで、参照元の表示が変わり得ることを編集者に示す。表示アプリがキャッシュを更新できるよう、変更した対象と参照元への影響を確認できる。
- 公開内容から必須の参照で参照されているコンテンツは、公開取り消しと、公開取り消しを含むごみ箱への移動・完全削除を行えない。参照元の公開内容から参照を除くか、参照元の公開を取り消してから操作する。本文のリンクは必須の参照と同じに扱う。
- 任意の参照だけで参照されているコンテンツは、公開取り消し、ごみ箱への移動、完全削除を行える。参照元の公開内容は変えず、取得では公開内容を持たない参照先を未設定として返す。参照先を再び公開すると、参照元の再公開なしに参照を返す。参照元の編集画面では参照切れを示す。
- 複数対象の公開取り消しでは、同時に取り消す対象間の参照を許容する。操作後も公開を続ける対象からの必須の参照は残さない。
- 下書きからの参照だけでは、参照先の公開取り消しやごみ箱への移動を妨げない。参照切れを修正箇所として示し、公開前に解消する。完全削除からの保護は7.2に従う。
- 履歴の復元は対象コンテンツの保存内容と参照情報を復元する。参照先の内容を自動で過去の版に戻さない。参照先の状態に応じて公開検証を行う。
- 当時の参照先や表示アプリまで含めたページ全体の再現は初期版に含めない。

### 5.3 プレビュー

- プレビューは、実際の表示アプリで、公開前の下書きを含むサイトを確認する。3.3のプレビュー取得で最新の内容を取得し、未公開のコンテンツと公開中のコンテンツの変更を、公開せずに確認できる。
- プレビュー取得は、9.3のプレビュー取得の許可を持つサーバー用トークンで行う。ブラウザ用トークンには許可しない。
- メンバーは役割によらず、認証を経て自分に紐付くトークンを得て、プレビュー取得できる。
- 編集者は、編集画面から対象コンテンツのプレビューを表示アプリで開ける。プレビュー先は、スキーマで定義するモデルごとの経路と、運用設定のプレビュー先の表示アプリのURLから決まる。経路には、コンテンツIDと一意な値を使える。経路に使う値が未設定の場合は、プレビューを開けない理由を示す。プレビュー先を定義していないモデルでは、プレビューを開く操作を示さない。
- プレビューを開く操作では、そのメンバーの認証を経て発行するサーバー用トークンを、プレビュー取得の許可だけを持たせて表示アプリへ渡せる。このトークンは有効期間を限り、9.3のメンバーに紐付くトークンの規則に従う。表示アプリへは一度だけ使える引き換えの値を渡し、表示アプリはサーバー側でそれをトークンに引き換える。トークンの値をブラウザへ渡さない。
- 手動発行したトークンで取得した下書きを誰に見せるかは、表示アプリが制御する。CMSはトークンの先の閲覧者を識別しない。
- 取得時点で保存済みの内容を返す。返した内容が下書きと公開内容のどちらかを識別できる。ごみ箱のコンテンツは返さない。
- 型を満たさない入力エラーのある下書きは返さず、エラー箇所を示す。型を満たさない入力エラーは、必須項目の欠落と、値の種類・選択肢・参照先の不適合とする。公開内容で代替しない。一覧取得では該当するコンテンツを結果に含めず、含めなかった対象を示す。
- 文字数・範囲・書式・件数の制約違反だけの下書きは返す。制約違反があることを識別できる。
- 一意性は公開時に確認する。一意な値によるプレビュー取得で複数のコンテンツが該当する場合は、重複を示し、一件を推測で選ばない。
- 参照先にも同じ規則を適用する。参照先の下書きに型を満たさない入力エラーがある場合や、参照先がごみ箱にある場合は、プレビューを完了できないことを示す。任意の参照でごみ箱にある参照先は、未設定として返す。
- 非公開のメディアも表示する。

### 5.4 表示アプリへの通知

- 公開・更新・公開取り消しを表示アプリへ伝えられる。公開中のコンテンツの公開は更新として伝える。公開中のコンテンツのごみ箱への移動は、公開取り消しとして伝える。公開内容の値の書き換えは、更新として伝える。下書きの保存と破棄、下書きだけの値の書き換えは伝えない。
- スキーマ移行による公開内容の変更も通知対象とする。スキーマの版、変更した対象、操作の種類を識別でき、参照元への影響を確認できる。通知に非公開の内容を含めない。
- 通知は公開状態の確定後に行い、取り消した操作や失敗した移行の変更を通知しない。通知の重複や到着順の逆転があっても、表示アプリが変更の順序を判別できる情報を提供する。
- 通知の宛先と秘密情報は、表示アプリへの通知設定として管理画面で管理する。変更には9.1の権限を必要とし、9.2の操作履歴に残す。
- 表示アプリへの通知が失敗した場合、状況確認と再試行ができる。未対処の失敗があることを、権限を持つメンバーが管理画面の利用時に気付ける。
- CMSでの公開、アプリへの通知、アプリ上の表示反映を区別する。CMSが確認できない表示反映を完了と表示しない。

## 6. スキーマの変更とコンテンツ移行

スキーマの変更は、一般的なORMのマイグレーションと同じく、コードで管理する移行定義を順に適用して行う。CMSと表示アプリの関係は、データベースとアプリケーションの関係と同じとし、移行を適用する時期と表示アプリを切り替える手順は開発者が決める。

スキーマの変更は、次の規則に従う。各節はこの規則を詳しく定める。

- スキーマは現在の定義だけを宣言する。開発者はスキーマを変更し、移行定義はスキーマの差分から生成する。移行定義は、保存済みのデータの解釈が変わる変更と、差分だけでは決まらない開発者の判断を順に記録する。
- 保存済みのデータの解釈が変わる変更は、コンテンツの構造の変更とする。フォームの回答は受付時の定義とともに保存した記録として移行しないため、フォームの変更は保存済みのデータの解釈を変えず、移行定義に含めない。
- 移行定義は、スキーマの差分と生成時の判断から決まる変更だけを持つ。別の項目への値の移し替えなど、差分から決まらないデータの変換は扱わず、4.2の値の書き換えで行う。
- 反映は、未適用の移行定義を順に適用し、移行定義を必要としない定義を置き換え、全体を一つの単位として確定する。
- 移行は前にだけ進む。適用した変更を戻す場合は、戻す変更を新しい移行定義として適用する。データを失い得る操作で失った値・項目・コンテンツは、移行では戻せない。
- 保存済みのコンテンツは、公開内容、下書き、ごみ箱、履歴のいずれも、移行の確定と同時に現行スキーマの形へ変換する。CMSは過去のスキーマで保存した値を読み取り時に解釈しない。
- 公開内容の変換は、条件を満たさない場合に移行を失敗させる。下書き・ごみ箱・履歴の変換は移行を失敗させず、条件を満たさない値を未設定または入力エラーとして扱う。

### 6.1 スキーマの版と移行定義

#### 状態と規則

- ワークスペース内のコンテンツとフォームの定義全体を、一つの現行スキーマとして管理する。通常の編集・公開・新規受付には現行スキーマを使う。過去のスキーマを並行運用しない。
- スキーマの各版は、取得結果とフォーム送信の型の形だけから求める識別子を持つ。型の形は、モデル・フォーム・項目・選択肢・ブロックの種類のキー、単一モデルと複数件モデルの別、値の種類、必須、項目のまとまり・繰り返しの構成、許可するブロックの種類、参照・問い合わせ対象に許可するモデル、画像の派生形式のキーとする。文字数・範囲・書式などの制約と検証、一意性、表示・運用の定義だけの変更では識別子を変えない。
- 識別子は、スキーマ全体と、モデル・フォームごとに求める。モデル・フォームごとの識別子は、その対象自身の型の形と、その対象の取得結果に現れる派生形式のキーから求め、参照先のモデルの型の形を含めない。開発者は、CMSに接続せずに手元のスキーマの識別子を得られる。
- スキーマは、コンテンツの構造、フォームの構造、表示・運用に使う定義からなる。

| 区分 | 含むもの | 変更の反映 |
|---|---|---|
| コンテンツの構造 | モデル・項目・選択肢・ブロックの種類のキー、単一モデルと複数件モデルの別、値の種類、必須、制約、一意性、参照を許可するモデル、項目のまとまり・繰り返しの構成、許可するブロックの種類 | 移行定義を適用して反映する |
| フォームの構造 | フォーム・項目・選択肢のキー、値の種類、必須、検証、問い合わせ対象に許可するモデル | 移行定義を必要とせず、反映時に現行スキーマの定義を置き換える。キーの変更は6.5に従って削除と追加として扱う |
| 表示・運用の定義 | 表示名称・順序、説明・入力例、初期値、一覧表示・検索・問い合わせ対象の表示に使う項目、6.4の非推奨、5.3のプレビュー先の経路、画像の派生形式 | 移行定義を必要とせず、反映時に現行スキーマの定義を置き換える |

- 移行定義は、開発者の手元でスキーマの差分から生成する。開発者は移行定義を手で記述する必要がない。生成した移行定義はスキーマと同じく利用者のコードを正本とし、利用者がリポジトリでレビュー・管理する。
- 移行定義は、CMSが利用者のコードを実行せずに解釈できるデータとする。
- 移行定義は順序を持つ。CMSは、適用済みの移行定義と適用後のスキーマの版をワークスペースごとに記録し、反映時に未適用の移行定義を順に適用する。同じ移行定義の列を複数のワークスペースへ適用でき、どのワークスペースでも同じ結果になる。
- コンテンツの構造の変更は、3.1の直接反映を除き、項目の追加を含めてすべて移行定義に記録する。反映するスキーマのコンテンツの構造は、現行スキーマに未適用の移行定義を順に適用した結果と一致させる。一致しない反映は拒否し、食い違う定義を示す。
- 直接反映によって、現行スキーマのコンテンツの構造が適用済みの移行定義を順に適用した結果と一致しない場合は、移行定義の適用を拒否し、食い違う定義を示す。直接反映で一致する構造に戻すと、移行定義を適用できる。
- 移行定義は一本の列とする。反映する移行定義の列は、ワークスペースの適用済みの列に未適用の移行定義を続けたものに限る。適用済みの移行定義の変更・削除と、適用済みの移行定義より前の位置への追加は、移行定義の列のまとめを除いて拒否し、食い違う移行定義を示す。適用後に変更を戻す場合は、戻す変更を新しい移行定義として追加する。
- 別々に作成した移行定義の列の分岐を、合わせて適用しない。後から反映する側は、未適用の自分の移行定義を除き、現在の列とスキーマの差分から生成し直す。
- 開発者は、連続する移行定義の列を一つの移行定義にまとめられる。まとめた移行定義は、まとめる前の列と同じ変更として扱う。まとめる前の列をすべて適用済みのワークスペースでは、まとめた移行定義を適用済みとして扱う。まとめる前の列の一部だけを適用済みのワークスペースへの反映は拒否し、未適用の移行定義を示す。
- フォームの変更は、保存済み回答を書き換えない。受付への影響は6.5に従う。

#### 操作と表示

- 開発者は、既存の移行定義を順に適用した構造と変更後のスキーマの差分から、CMSに接続せずに移行定義を生成できる。差分だけでは決まらない判断は、生成時に開発者へ確認して移行定義に記録する。
- 開発者は、CMSに接続せずに、スキーマのコンテンツの構造と移行定義を順に適用した結果の食い違いを検出できる。
- 生成する移行と生成時に確認する判断は、6.2に従う。
- 反映前に、対象ワークスペースの適用済みの移行定義、未適用の移行定義、手元の移行定義との食い違いを確認できる。この確認はデータを変更しない。
- 反映前に、対象ワークスペースの現在のデータへ未適用の移行定義を適用した場合の結果を、データを変更せずに確認できる。これを適用の事前確認と呼ぶ。結果には、移行が失敗する対象と理由、6.2のデータを失い得る操作で失う値・項目・コンテンツの対象と件数、公開内容が変わるコンテンツ、変換後に入力エラーを持つ下書きを含む。結果は確認時点のデータに基づき、適用時の成功を保証しない。
- スキーマの版ごとに、適用した移行定義、含まれるデータを失い得る操作、日時、反映に使ったトークンとその発行者を確認できる。直接反映による版は、直接反映によることと、失った値・項目・コンテンツの種類を確認できる。
- 現行スキーマのコンテンツの構造が、直接反映によって適用済みの移行定義と食い違っているかを確認できる。

### 6.2 スキーマの変更と生成する移行

開発者はスキーマを変更し、移行定義は差分から生成する。コンテンツの構造の変更は、次の表に従って生成する。どの変更にも生成する移行があり、対応する移行のない変更は削除と追加として生成する。

| スキーマの変更 | 生成する移行 | 生成時に開発者へ確認すること | 既存データへの影響 |
|---|---|---|---|
| モデル・項目・選択肢・ブロックの種類の追加 | 追加 | 必須の項目では、未設定の既存の値に入れる補完値。指定は任意 | 補完値を指定した場合は、未設定の値に入れる |
| 同じ階層での削除と追加 | キーの変更、または削除と追加 | キーの変更として扱うか | キーの変更では引き継ぐ。削除と追加では失う |
| 任意項目の必須化 | 必須の変更 | 補完値。指定は任意 | 補完値を指定した場合は、未設定の値に入れる |
| 制約・一意性・参照を許可するモデルの変更 | 制約の変更 | なし | 値を変えない |
| 変換規則のある組み合わせでの値の種類の変更 | 値の種類の変更 | 変換できない値を失うこと | 変換規則で変換する。変換できない値は失う |
| 変換規則のない組み合わせでの値の種類の変更 | 同じキーの項目の削除と追加 | 値を失うこと | 失う |
| 選択肢・ブロックの種類の削除 | 削除 | 選択肢の置き換え先。別の選択肢または未設定 | 置き換える、または取り除く |
| 項目・モデルの削除 | 削除 | 値・項目・コンテンツを失うこと | 失う |
| 繰り返しの内外をまたぐ構造の組み替え、単一モデルと複数件モデルの間の変更 | 削除と追加 | 値・コンテンツを失うこと。値を保つ場合の段階的変更の手順 | 失う |

- フォームの変更は、キーの変更を含めて移行定義を生成せず、スキーマの反映で行う。フォームとその項目のキーの違いは、6.5に従って削除と追加として扱う。
- 生成時の判断は、移行定義に記録する。データを失い得る操作は、生成時に対象を示して開発者の確認を得てから生成し、確認を移行定義に記録する。移行定義のレビューと適用を、その操作の承認とする。
- 差分から決まらない値の移し替えは、段階的変更で行う。新しい項目を追加するスキーマの変更を反映し、9.3のコンテンツ管理の許可による4.2の値の書き換えで値を移し、古い項目を削除するスキーマの変更を反映する。6.4の非推奨を併用できる。値の書き換えは、公開内容、下書き、ごみ箱のコンテンツの値を移せる。履歴の版の値は移さず、古い項目の削除で履歴から取り除く。
- 項目・モデル・ブロックの種類の削除、置き換え先に未設定を指定する選択肢の削除、値の種類の変更、削除と追加として生成した変更は、既存の値・項目・コンテンツを取り除くか未設定にし得るため、データを失い得る操作とする。適用は6.3に従う。
- 値の種類の変更では、CMSが定める変換規則で既存の値を変換する。変換規則と、変換できる値の種類の組み合わせを開発者に示す。変換できない値を持つ公開内容が一件でもあれば、移行は失敗する。下書き・ごみ箱・履歴の変換できない値は未設定とする。下書き・ごみ箱では下書きの入力エラーとして扱い、履歴の版では7.1に従って復元時に示す。
- モデルのキーの変更では、コンテンツID、公開内容、下書き、状態、履歴、運用設定を引き継ぐ。項目のキーの変更では、履歴を含めて値を引き継ぐ。
- 補完値と置き換え先は、公開内容、下書き、ごみ箱、履歴のすべてに適用する。補完値は未設定の値にだけ入れ、設定済みの値を変えない。選択肢の置き換え先には、別の選択肢と未設定を指定できる。削除するブロックの種類のブロックは、すべての内容から取り除く。
- 必須化と制約の強化は、補完値による補完を除いて既存データの値を変えない。補完後の公開内容が変更後の条件を満たさない場合、移行は失敗する。下書き・ごみ箱の違反は下書きの入力エラーとして扱い、履歴の版の違反は7.1に従って復元時に示す。
- 項目の削除では、その項目の値を、公開内容、下書き、ごみ箱、履歴から取り除く。
- モデルの削除では、そのモデルのコンテンツを、公開中のものを含めて、ごみ箱と履歴とともに完全削除する。公開中だったコンテンツは、5.4で公開取り消しとして伝える。他のモデルからの参照定義は、同じ変更で取り除く。他のコンテンツの公開内容から本文のリンクなどで参照されている場合、移行は失敗する。
- フォームの削除は6.5に従う。
- データを失い得る操作で取り除いた値・項目・コンテンツは、移行の確定後、取得・表示・検索・復元に含めない。移行では戻せず、戻す手段は10.2の設置全体のバックアップからの復旧とする。
- 削除したキーは、後の変更で別の対象に再利用できる。削除前の値は移行で取り除いているため、新しい対象へ戻らない。運用設定も新しい対象へ引き継がない。フォームの回答と通知定義でのキーの扱いは、8.2と8.3に従う。

### 6.3 適用

#### 状態と規則

- 移行は、そのワークスペースのコンテンツの公開内容、下書き、ごみ箱、履歴を、確定と同時に現行スキーマへ変換する。保存済み回答は移行せず、8.2に従って受付時の定義で扱う。
- 未適用の移行定義の適用と、移行定義を必要としない定義の置き換えを、一つの単位として確定する。失敗した場合は、現行スキーマ、データ、運用設定を変更しない。
- 確定するまでは、既存の公開内容を既存の構造で配信する。移行途中の内容を、公開取得でもプレビュー取得でも返さない。一つの取得結果に、移行前後の構造を混在させない。
- 公開内容は、変換後も公開時の検証を満たす必要がある。満たさない公開内容が一件でもあれば、移行は失敗する。下書き・ごみ箱・履歴の変換は移行を失敗させない。下書きと履歴の版は、変換後に入力エラーを持ってよい。
- 移行によって下書きを公開しない。公開内容と下書きの対応を入れ替えない。
- 適用中は、対象コンテンツの編集・公開を止めてよい。
- 移行は、スキーマ反映の許可を持つトークンで適用する。管理画面での承認を必要としない。
- 6.2のデータを失い得る操作は、生成時の確認と移行定義のレビューで承認したものとし、反映の要求で改めて認めることを必要としない。現在のデータへの影響は、6.1の適用の事前確認で確認する。
- 前提とする現行スキーマの版が反映中に変わった場合、その反映は拒否する。

#### 操作と表示

- 進行状況、成功・失敗、失敗の理由と対象を確認できる。公開時の検証を満たさずに失敗した場合は、該当するコンテンツと項目を示す。
- 移行で編集・公開を止めている対象と状態が、利用者に分かる。
- 変換後に入力エラーを持つ下書きは、エラー箇所を示し、編集を続けられる。4.3の絞り込みで、該当する下書きを一覧できる。
- データを失い得る操作の生成時と適用の事前確認で、失う値・項目・コンテンツを移行では戻せず、戻す手段が10.2の設置全体のバックアップからの復旧に限られることを示す。

### 6.4 表示アプリとの切り替え

- CMSは、表示アプリがどの版のスキーマに対応しているかを判断しない。3.2の識別子の一致は示すが、互換性は判断しない。表示アプリの配信完了を、移行を適用する条件にしない。
- 開発者は、移行の適用と表示アプリの配信の順序を決める。互換性のない変更を適用した後、変更前のスキーマを前提とする表示アプリの表示の継続は保証しない。
- 段階的変更でも、各時点の現行スキーマは一つとする。一つのスキーマ内に新旧の項目を一時的に共存させられる。
- 項目を置き換える段階的変更では、新しい項目の追加、古い項目への非推奨の指定、古い項目の削除を、別々の反映としても同じ反映としても確定できる。反映の間に、値の書き換えによる値の移し替えや表示アプリの切り替えを挟める。
- 反映は未適用の移行定義をすべて適用し、一部の移行定義だけを適用しない。
- 開発者は、コンテンツのモデル・項目・選択肢・ブロックの種類に、スキーマの属性として非推奨を指定できる。非推奨の指定は、保存済みの値、取得結果、入力検証を変えず、生成する型で非推奨として示す。必須の項目には非推奨を指定できない。必須の項目を段階的に置き換える場合は、任意化と非推奨の指定を同じ反映で行える。3.1の検証で必須の項目への非推奨の指定を検出した場合は、この手順を示す。
- 編集画面では、非推奨の対象を非推奨と示して読み取り専用とし、新たに使えない。既存の値は値の書き換えで変更する。非推奨のモデルのコンテンツも、公開取り消し、ごみ箱への移動、下書きの破棄はできる。

### 6.5 フォーム変更時の受付

#### 状態と規則

- フォームの変更を反映するまでは、現行の定義で受付を続ける。
- スキーマの反映は、通知定義の参照を理由に拒否しない。反映で生じた通知定義の参照の不整合は8.3に従って扱い、受付と通知を止めない。スキーマ変更によって運用設定を自動で補正・削除しない。
- 定義の切り替えと受付が重なっても、一件の送信には、切り替え前または切り替え後のいずれか一組のフォーム定義と通知定義を適用する。通知対象は8.1に従って受付時に確定し、受付後の通知先の変更は8.3に従う。
- 送信は、受付時点の現行の定義で検証する。定義の変更前の表示から送られた送信も同じ扱いとし、現行の定義を満たさない送信は、項目ごとの理由を付けて入力不備として拒否する。存在しないフォームへの送信は拒否する。
- 保存済み回答とその通知は、受付時の項目、選択肢、検証結果、通知定義に基づいて扱う。フォームや通知定義の変更、受付停止、フォームの削除だけで、保存済み回答や未送信の通知を取り消さない。
- フォームは、受付状態によらずスキーマの反映で削除できる。フォームを削除すると新規受付を終了する。保存済み回答は、受付時のフォームと通知定義の情報とともに、保持方針に従って保持する。
- フォームとその項目のキーの変更は、移行定義に記録せず、削除と追加として扱う。保存済み回答を新しいキーへ読み替えず、削除したフォームの運用設定を新しいフォームへ引き継がない。新しいフォームは3.1に従って受付停止状態で作成する。

#### 操作と表示

- 反映前に、反映によって不整合となる通知定義の参照、削除して受付を終了するフォーム、キーの違いから削除と追加として扱うフォームと項目を、データを変更せずに確認できる。反映結果にも同じ内容を示す。
- フォームのキーを受付を止めずに変える場合は、新しいキーのフォームを追加して運用設定を整えて受付を有効にし、表示アプリを切り替えてから古いフォームを削除する。
- 定義の変更で受け付けられなくなった送信では、表示アプリが入力を保持し、現行のフォームで修正・再送を促せる。
- 削除したフォームの保存済み回答を、削除済みフォームの回答として閲覧・削除し、通知を再試行できる。

## 7. リビジョン、保持、削除

### 7.1 履歴と復元

- 下書きの保存・公開・下書きの破棄・公開取り消し・復元・移行・値の書き換えなど、利用者が理解できる単位でコンテンツの履歴を確認できる。公開内容だった版と下書きだった版を区別できる。
- 実行者、日時、変更内容を確認し、版の差分を比較できる。
- 過去の内容は、状態によらず下書きとして復元する。復元だけでは公開せず、公開中のコンテンツでは公開内容と配信を変えない。
- 復元前に最新の内容との差分を確認できる。置き換え前の内容を履歴から取り戻せ、他の操作による変更を気付かず上書きしない。
- 履歴は、6.3の移行で下書きと同じ規則に従って現行スキーマへ変換する。キーを変更した項目の値は変更後の項目へ引き継ぎ、値の種類を変更した項目の値は6.2の変換規則で変換する。削除した項目の値は取り除き、変換できない値は未設定にする。
- 復元した内容が現行の制約を満たさない場合は、下書きの入力エラーとして示す。
- 履歴は現行スキーマで確認・復元する版とし、操作の監査記録として扱わない。移行前の保存内容は再現しない。削除したモデルのコンテンツの履歴は残さない。

### 7.2 保持と削除

#### 状態と規則

- ごみ箱からの復元と、履歴を含む完全削除を区別する。
- コンテンツの公開内容と下書き、保持対象の履歴・回答、ごみ箱のコンテンツから必要とされる参照先は、完全削除と自動整理から保護する。任意の参照だけで参照されている参照先は保護しない。メディアの削除は4.4に従う。
- 送信時の情報だけで解釈できる問い合わせ対象は、8.1に従って参照先の保持を必須としない。
- 複数対象を明示して完全削除する場合は、同じ操作で削除する対象間の参照を許容する。削除後に保持する対象からの必要な参照は残さず、全対象の権限と削除条件を満たしてから一括で確定する。
- 削除に伴って無関係なコンテンツや履歴を自動で連鎖削除しない。
- リビジョン、ごみ箱、保存したフォーム回答に標準の保持方針を用意する。フォーム回答の保持方針は、コンテンツ履歴の保持方針と分ける。
- 保持方針に従って自動整理する。リビジョンの自動整理は履歴だけを対象とし、コンテンツの公開内容と下書きを削除しない。

#### 操作と表示

- 完全削除の対象と、参照先・履歴への影響を確認できる。
- 完全削除に必要な参照の解消方法を示す。コンテンツの公開内容・下書きの修正や、保持中の履歴・回答の削除が必要な場合は、各対象を扱える権限と明示的な操作を必要とする。
- 権限を持つ運営者が保持方針を変更できる。整理対象と復元できなくなる条件を運営者が確認できる。
- バックアップと外部送信先に残る情報は、CMSの通常データと区別して説明する。

## 8. フォーム受付と通知

### 8.1 フォームの利用

#### 状態と規則

- フォームは受付中または受付停止のいずれかとする。
- フォームは、受け付けた回答を8.2に従って保存し、有効な通知先へ通知する。有効な通知先を一件以上設定する。
- 初期版では、送信の受付時に有効なすべての通知先を、その送信の通知対象として確定する。回答内容や問い合わせ対象に応じた通知先の振り分けは行わない。通知先がゼロの状態では受付を有効にできず、新規送信も受け付けない。
- 通知先など運営者用の設定を、送信者が自由に変更できない。
- フォームの初期版の項目型は、テキスト、数値、真偽値、日付、日時、単一選択、複数選択、公開コンテンツへの参照とする。
- 必須、文字数、数値・日付・日時の範囲、テキストの書式、選択肢と選択数、真偽値が真であること、同じ型の二項目の一致を標準の検証として定義できる。テキストの書式は、メールアドレス・URLの形式と、開発者が定義するパターンとする。形式の検証は連絡先の所有や到達可能性を保証しない。
- 必須の真偽値では、値が存在することと真であることを区別する。同意チェックなどには真であることを条件として指定できる。
- フォームでは、メディア、リッチテキスト、項目のまとまり、繰り返し、ブロックを扱わない。利用者独自の検証関数をCMS内で実行しない。
- 未入力の必須項目を勝手に補ったり、入力内容を黙って捨てたりしない。初期値の定義があっても、必須項目の欠落を受付時に補わない。
- 定義されていない項目、許可されていない値、変更できない受付条件を含む送信は拒否する。
- フォームのコンテンツ参照の項目で指定したコンテンツを、問い合わせ対象と呼ぶ。一つのフォームに、問い合わせ対象の項目を複数定義できる。
- 問い合わせ対象として指定できるコンテンツは、項目ごとに許可したモデルの公開中のコンテンツに限る。指定値を検証し、公開権限や通知先の指定に利用しない。
- 問い合わせ対象は、受付時に公開状態と許可範囲を検証する。対象のモデルキー、コンテンツID、公開内容の表示名称を、送信時の情報として回答に含める。表示名称に使うテキスト項目はスキーマで指定する。一意な値を定義している場合は、その値も含める。
- 問い合わせ対象の更新、公開取り消し、削除によって、受付済みの通知や回答の解釈を妨げない。送信時の情報を保持した回答・通知だけを理由に、元のコンテンツの完全削除を禁止しない。

#### 操作と表示

- フォーム専用サービスを追加契約せずに、問い合わせを受け付けられる。
- メール通知に必要な送信設定を行い、動作確認できる。既存のメール送信環境を利用できる。
- フォームごとの通知先と受付の有効・無効を管理できる。
- コンテンツを作成せずにフォームを利用できる。一般的な問い合わせとして、コンテンツと無関係に利用できる。
- 必要な場合は、商品や記事などを問い合わせ対象として紐付けられる。
- 通知と保存回答の表示には送信時の問い合わせ対象の情報を使い、現在の名称や内容で置き換えない。保存済み回答から通知を再試行する場合も同じ情報を使う。現在のコンテンツへのリンクは、送信時の情報と区別し、閲覧者の権限でアクセスできる場合に表示する。
- 入力制約を検証し、送信者が項目ごとの問題を理解して修正できる。拒否した送信には修正できるエラーを返す。
- 定義の変更前の表示から送られた送信も、6.5に従って現行の定義で検証する。受け付けられない場合は、表示アプリが入力内容を保持して修正を促せる。
- フォーム送信は、9.3のフォーム送信の許可を持つトークンで行う。サーバーからの送信と、ブラウザからの直接の送信のどちらにも対応する。トークンはアプリを認可し、送信者本人を確認しない。
- 迷惑送信を抑制できる。ブラウザ用トークンの値が知られることを前提に、送信制限を設ける。
- 受付結果と受付失敗の理由を、8.2に従って区別できる。受付できない場合は受付完了を返さない。

### 8.2 受付と回答の保存

#### 状態と規則

一件の送信の受付結果は、次のいずれかとする。

| 受付結果 | 意味 |
|---|---|
| 受付完了 | 入力検証を終え、回答が保存され、CMSの通常の停止・再起動があってもその回答の通知が行われる状態になった |
| 受付失敗 | 受付完了の条件を満たさなかった。受付時の拒否を含む |

- 受付失敗には理由を付け、受付停止、入力不備、フォームが存在しない、混雑・送信制限、保存の失敗を区別できる。
- 受付結果は、通知の送信結果を待たずに返す。通知の送信失敗は受付失敗にしない。
- 保存に失敗した回答を受付完了と扱わず、通知しない。回答だけが保存され、その通知が行われないまま失われる状態を生じさせない。保存基盤を失う災害時の復旧は10章に従う。
- CMSは、送信とは別に受付結果を確認する手段を提供しない。同じ内容の再送を重複として統合せず、新しい送信として受け付ける。通信断などで送信者が再送した場合は、重複した回答と通知が生じ得る。
- 保存した回答を公開コンテンツとして扱わない。
- 回答は、送信時の項目、選択肢、入力内容、問い合わせ対象の情報を保持する記録とする。フォームの変更や移行によって過去の回答を書き換えず、読み替えもしない。
- 通知と手動再試行には保存済み回答を使う。通知のために入力内容の別の保持期限を設けず、回答の削除後に通知用の入力内容を残さない。
- 各回答には受付時の保持方針を適用する。保持方針の変更は以後の新規回答に適用する。既存回答への適用は、権限を持つ担当者が明示的に行う場合に限る。
- 通知の成功・失敗・再試行によって回答の保持期間を変更しない。
- 回答を削除した後は、その回答を使う未送信の通知や再試行を開始しない。通知のために削除した入力内容を別に残したり復活させたりしない。削除時点で送信中の通知や、外部で受理済みの通知を取り消せることは保証しない。
- 通常のログ、操作履歴、エラー情報へ回答本文や連絡先を記録しない。

#### 操作と表示

- 送信者に、運営者用の通知先や接続設定の詳細を明かさない。
- 許可された担当者が、保存した回答を閲覧・削除できる。
- 保存回答の一覧を、受付日時で並べ、フォーム、受付期間、通知の送信結果で絞り込める。スキーマで指定した一覧表示用の項目の部分一致で検索でき、特定の送信者の回答や重複した回答を見つけて削除できる。一覧表示・検索では、現行スキーマの一覧表示用の項目のキーを、各回答の受付時の項目のキーと照合する。キーの一致だけで照合し、項目の変更の経緯を追わない。
- 既存回答へ保持方針の変更を適用する場合は、適用範囲と削除予定を示して確認する。
- 対応状況の管理、担当者割り当て、顧客管理まで含めることは求めない。管理画面での回答の一括エクスポートは初期版に含めない。

### 8.3 通知メールの定義と送信結果

#### 状態と規則

- 通知メールの件名・本文・送信者の表示名・返信先を、通知定義と呼ぶ。通知定義はフォームごとの運用設定として管理画面で定義し、コードとの二重定義を必要としない。
- 通知定義は、現行のフォームスキーマの項目を参照する。通知定義の編集では、存在しない項目と、用途に合わない型の項目を参照できない。
- 通知定義は、フォームの項目をキーで参照する。
- スキーマの反映で、参照するキーの項目が現行のフォームになくなった場合と、用途に合わない型に変わった場合は、その参照を不整合として扱う。項目のキーの変更も、変更前のキーへの参照を不整合にする。不整合のある通知定義でも受付と通知を止めない。通知では、不整合のある参照を値の代わりに不整合と分かる表示で示す。返信先の参照が不整合の場合は、返信先を指定せずに送る。
- 通知定義では、回答の項目の値、回答の全項目の一覧、選択肢の表示名称、複数選択の列挙、未入力の項目の出し分け、問い合わせ対象の送信時の情報、受付日時を扱える。メールアドレス形式の回答項目を返信先に指定できる。任意の条件式と関数による本文の生成は初期版に含めない。
- 回答の全項目の一覧は、受付時のフォームの項目を表示名称・順序に従って列挙する。フォームの項目の追加・削除で、全項目の一覧を使う通知定義の変更を必要としない。
- 各送信の受付時に、通知定義と通知対象を確定する。その後の通知と手動再試行の内容には受付時の通知定義を使う。通知定義の更新は、以後の新規送信に適用する。
- 最初の通知は、受付時に確定した通知対象のうち、送信時点でも有効な通知先へ送る。受付後に通知先から外した宛先には、その後の通知も手動再試行も送らない。
- 通知の送信結果は、未送信、送信成功、送信失敗のいずれかとする。送信対象としたすべての宛先についてメール送信基盤の受理を確認した場合に送信成功とする。一部だけの成功、タイムアウトなどで成功を確認できない場合、有効な宛先が残らない場合は送信失敗とする。
- 通知の送信成功は、メール送信基盤が受け付けたことを意味する。受信箱への到着や開封は、通知の成功の条件にしない。
- 通知の送信失敗は、通知が届いていないことを保証しない。メール送信基盤の受理後に通信が途切れた場合など、成功を確認できなくても通知が届いている場合がある。メール通知が厳密に一度だけ届くことは保証しない。
- 送信に失敗した通知は、自動で再試行しない。送信を試みた後に成功を確認できない場合も同じ扱いとする。CMSの停止・再起動や処理のやり直しを理由に、送信成功を確認済みの通知を再送しない。
- 手動再試行は、再試行の時点で有効な通知先のうち、その回答の通知の送信成功を確認できていない宛先へ送る。受付後に修正・追加した通知先も宛先に含め、成功を確認済みの宛先へ再送しない。
- 送信接続設定は、メール送信基盤への接続先、認証情報、接続条件とし、ワークスペースごとに一つ持つ。ワークスペースの全フォームが同じ設定を使う。
- 送信では現在の送信接続設定を適用し、送信中の通知には途中適用しない。未送信の通知と手動再試行には更新後の設定を使う。削除済みフォームの保存回答に対する通知にも同じ規則を適用する。
- 接続設定を更新しても、保存済み回答、受付時の通知定義、回答の保持方針は変更しない。
- 受付中のフォームから有効な通知先をなくす変更と、送信接続設定を使えない状態にする変更は拒否する。受付停止中は修正でき、通知先と送信接続設定がそろうまで受付を再開しない。

#### 操作と表示

- 変更を拒否した場合は、問題のある定義・設定と理由を示す。
- 権限を持つメンバーが、管理画面で通知定義を編集できる。参照する項目は現行のフォームスキーマの項目から選び、入力例による表示を送信前に確認できる。9.1の通知設定の権限を必要とする。
- 通知定義の参照の不整合が残っていることを、通知設定の権限を持つメンバーが管理画面の利用時に気付ける。不整合のある参照と理由を示し、修正できる。
- 権限を持つ管理者が、送信接続設定の動作確認と更新を行える。更新では影響するフォームを示す。9.1の通知設定の権限を必要とする。
- 設定変更と送信を追跡できる記録を残し、認証情報そのものは操作履歴へ記録しない。
- 運営者が、回答ごとの通知の送信結果と失敗の理由を確認し、必要な対処を把握できる。送信者に同じ回答の再送を求めない。送信中などの細かな進行状態とその管理方法は設計で定める。
- 通知の送信失敗が未対処で残っていることを、通知設定の管理権限を持つメンバーが管理画面の利用時に気付ける。失敗の発生は、フォームの通知と同じ送信経路だけに依存せずに知らせられる。知らせる内容に入力内容を含めない。
- 権限を持つ担当者が、通知の送信に失敗した保存済み回答から通知を手動で再試行できる。再試行で回答を複製しない。再試行の操作を誤って繰り返しても、一件の再試行として扱う。
- 手動再試行の前に、宛先と、受付時の通知対象から外れた宛先・加わった宛先を確認できる。成功を確認できなかった宛先にも届いている可能性を示す。
- CMS外のメール送信環境や受信箱には通知内容が残り得る。CMSが保持するデータと、外部送信先での保持を区別して説明する。

## 9. ワークスペース、権限、認証

### 9.1 ワークスペースと権限

#### 状態と規則

- ワークスペースごとに、スキーマ、コンテンツ、メディア、フォーム、メンバー、アクセス権を管理する。一つの設置で複数のワークスペースを扱える。
- 利用を許可されていないワークスペースの情報へアクセスできない。
- 権限はワークスペース単位で付与する。
- メンバーの解除・権限変更後は、新たな操作に最新の認可を適用する。接続中のセッションも次の操作から対象とする。
- 所有者が不在になる解除を防ぐ。
- 所有者、管理者、編集者、閲覧者に相当する標準の役割を提供する。詳細な権限表は設計で定める。
- スキーマ変更や運用設定と、日常のコンテンツ編集を権限上区別する。
- 保存した回答の閲覧権限を、コンテンツの編集権限と区別する。
- 通知先と送信接続設定の変更は、入力内容の外部送信先を決定する権限として扱う。この権限は保存回答の閲覧権限とは独立して付与できる。
- 公開、スキーマ変更、フォーム回答の閲覧・削除、通知設定、受付管理（受付状態・回答の保持方針）、メンバー管理を、それぞれの責務に応じて許可できる。保存済み回答の通知結果の確認と手動再試行、8.3の通知定義の変更には、通知設定の権限を必要とする。
- 下書きの保存・破棄と、下書きの値の書き換えはコンテンツの編集権限で行える。公開内容を変える公開・公開取り消し・値の書き換えには公開権限を必要とする。公開権限を持たない編集者も、公開中のコンテンツの変更を下書きとして準備できる。
- 9.3のトークンの手動発行・失効は、アプリへ操作を委ねる操作として扱い、日常のコンテンツ編集と分けて許可する。メンバーの認証を経た発行は、5.3と9.3に従う。
- プレビュー先の表示アプリのURLの変更は、メンバーに紐付くトークンの渡し先を決めるため、トークンの手動発行と同じ権限を必要とする。
- メディアの公開・非公開化は、登録・説明編集と分けて許可できる。
- 一括操作にはすべての対象への権限を必要とする。
- スキーマ変更権限は、移行と直接反映による値・コンテンツの消去と公開内容の変更、フォームの削除による受付の終了を含む。移行と直接反映以外の操作では、スキーマ変更権限でコンテンツの編集・削除・公開やメディア公開の権限を代替しない。
- 管理画面、9.3のトークンのいずれの経路から操作しても、同じ認可と入力検証を適用する。

#### 操作と表示

- ワークスペースの作成と初期所有者の設定は、ホスティング運営者が導入・運用手順で行う。設置のデータが空の状態で起動するときは、10.1の初期構成で宣言できる。特定のワークスペースの利用終了とデータの消去も、ホスティング運営者が10.1の手順で行う。メンバーによる運用中のワークスペースの作成機能と、管理画面での運用中のワークスペース単位の削除機能は初期版に含めない。
- メンバーを招待し、権限の変更と利用の解除ができる。
- ワークスペースの所有者を変更できる。
- 標準の役割だけで表現できない担当者の範囲も設定できる。所有者は、問い合わせ担当者など必要な利用者にアクセスを許可できる。
- 通知先・送信接続設定の権限を設定するときは、通知経由で入力内容を取得できることを示す。

### 9.2 認証

#### 状態と規則

- 人のセッションと、9.3のアプリのトークンを区別する。
- 招待には対象と有効期限を設ける。使用済み・失効済みの招待では参加できない。
- 繰り返し失敗するログインの試行を制限する。
- 資格情報、サーバー用トークン、通知設定の秘密情報を、公開データや通常のログに含めない。
- 権限、メンバー、トークンの発行・失効、スキーマ、通知定義、通知先・送信接続設定、表示アプリへの通知設定、プレビュー先の表示アプリのURL、保持方針の変更、移行の適用、直接反映、初期構成の読み込みと紐付けを操作履歴に残す。履歴には秘密情報とフォーム回答の入力内容を含めない。

#### 操作と表示

- 人はログイン・ログアウトできる。本人確認を伴うアクセス回復手段を提供し、セルフホスティングでは外部メールが使えない場合の管理者復旧手順も用意する。
- 人は多要素認証を設定できる。所有者は、ワークスペースのメンバーに多要素認証を必須にできる。
- 権限を持つメンバーが、ワークスペースの操作履歴を確認できる。

### 9.3 アプリの接続と認可

表示アプリやスクリプトなどのアプリは、ワークスペースが発行したトークンを持ち、トークンが許可する操作を行う。人のセッションとアプリのトークンを区別する。

#### 状態と規則

- アプリからの公開取得、プレビュー取得、フォーム送信、スキーマの反映、コンテンツ管理は、トークンで認可する。有効なトークンのない要求は受け付けない。
- トークンはワークスペースごとに発行し、発行元のワークスペースだけを操作対象とする。アプリの接続先は使うトークンで決まり、本番と検証の切り替えはトークンの切り替えで行える。
- トークンは次の許可の組み合わせを持つ。ワークスペース内の対象の範囲でも絞り込める。範囲の単位は設計で定める。

| 許可 | できること |
|---|---|
| 公開取得 | 3.3の公開取得 |
| プレビュー取得 | 3.3のプレビュー取得。5.3に従う |
| フォーム送信 | 8章のフォーム送信 |
| スキーマ反映 | 3.1のスキーマの反映と直接反映、6.1の適用状況の確認と適用の事前確認、6.3の移行の適用 |
| コンテンツ管理 | 4章・5章のコンテンツとメディアの操作。作成、最新の内容の取得、下書きの保存・破棄、値の書き換え、公開、公開取り消し、ごみ箱への移動と復元、完全削除、メディアの登録・公開を含む。管理画面と同じ規則と入力検証に従う |

- トークンは、保管先によって次のいずれかの種類とする。

| 種類 | 保管先 | 持てる許可 |
|---|---|---|
| サーバー用 | サーバー、ビルド環境、開発者の手元など、値を秘匿できる環境 | すべての許可 |
| ブラウザ用 | ブラウザ、SPA、配布するアプリなど、利用者から値が見える環境 | 公開取得、フォーム送信 |

- ブラウザ用トークンは、値が第三者に知られる前提で扱う。知られても、公開内容の取得とフォーム送信を超える操作を許さない。利用元の限定と利用量の制限を設定できる。利用元の限定を本人確認として扱わない。
- トークンは、管理画面での手動発行、認証を経た発行、または10.1の初期構成での宣言で得る。
  - 手動発行したトークンはアプリに紐付け、発行者の解除や権限変更で失効しない。本番の配信・受付・反映は、このトークンでメンバーの在籍に依存せずに行える。
  - 初期構成で宣言したトークンは、手動発行したトークンと同じ規則に従い、初期構成の所有者を発行者とする。値は初期構成で宣言し、宣言した者が保管する。
  - メンバーの認証を経て発行したトークンはそのメンバーに紐付け、メンバーの権限の範囲で認可する。メンバーの解除と権限の縮小は次の要求から適用する。
- トークンに与える許可は、発行者が持つ権限の範囲に限る。スキーマ反映の許可にはスキーマ変更権限を必要とする。コンテンツ管理の許可には、対象の操作に必要な権限を必要とする。
- トークンには、表の許可以外の操作を許可しない。回答の閲覧・削除、運用設定とメンバーの変更は管理画面で行う。
- 失効・期限切れのトークンは、次の要求から拒否する。同じ用途のトークンを複数持て、新しいトークンへ切り替えてから古いトークンを失効させることで、配信と受付を止めずに入れ替えられる。
- トークンに有効期限を設定できる。期限を設けない場合は、発行時に明示する。
- サーバー用トークンの値は発行時にだけ示し、後から表示しない。トークンの値は9.2に従って保護する。

#### 操作と表示

- 権限を持つメンバーが、トークンを発行・失効できる。
- トークンごとに、名称、種類、許可、範囲、発行者、発行日時、有効期限、最終利用日時を確認できる。
- 有効期限が近いトークン、発行者が解除されたトークン、長く使われていないトークンを見つけて見直せる。
- トークンの発行・失効を操作履歴に残す。

## 10. 運用と品質

### 10.1 導入と更新

- セルフホスティングの導入、管理者設定、保存先や通知の動作確認を、手順に沿って完了できる。
- ホスティング運営者は、設置の初期構成として、ワークスペース、所有者、トークン、運用設定を宣言できる。CMSは、設置のデータが空の状態で起動したときにだけ初期構成を読み込み、データがある状態の起動やバックアップからの復旧では読み込まない。読み込んだ後は、管理画面での設定を正本とする。
- 初期構成で宣言したモデル・フォームごとの運用設定は、対象をキーで指定し、そのキーの対象をスキーマの反映で作成したときに紐付ける。紐付けた後の運用設定は、3.1の規則に従う。紐付けを待つ運用設定を確認できる。
- 不正な初期構成では起動せず、該当する宣言と理由を示す。初期構成の運用設定は、管理画面での設定と同じ検証に従う。初期構成に含む秘密情報は、9.2に従って保護する。
- 更新前に必要な作業と影響を確認できる。
- 対応する実行環境と必要な資源を示す。保存容量や通知用の空き容量が不足する場合は運営者が確認できる。
- 更新に必要な停止時間と復旧方法を示す。更新に失敗した場合に、データを壊さず復旧できる手順を提供する。
- 特定のワークスペースの利用終了時は、ホスティング運営者がそのワークスペースの配信・受付・通知を終了し、保存データ、回答、メディア、資格情報を消去する手順を示す。他のワークスペースに影響を与えない。
- 設置全体の利用終了時は、ホスティング運営者が配信・受付・通知を終了し、保存データ、メディア、資格情報、バックアップを整理する手順を示す。
- どちらの利用終了でも、未完了の通知と失われるデータを確認でき、バックアップと外部送信先に残る情報を区別する。

### 10.2 バックアップと復旧

- スキーマ、コンテンツ、履歴、メディア、回答、運用設定、アクセス権、受付結果と通知の送信結果を、整合性を保ってバックアップ・復旧できる。削除済みフォームの回答と、適用済みの移行定義の記録も対象に含める。
- バックアップを保護し、認可されたホスティング運営者だけが取得・復旧できる。秘密情報を別管理する場合は、その復旧条件を示す。
- バックアップには取得時点の保存回答が残り得る。通常データの削除とは別に、バックアップの保持・削除期限を定める。
- 復旧時は、復旧点、失われる可能性のある期間、期限切れデータ、保存済み回答に対する通知の送信結果を確認してから利用を再開する。
- 復旧で戻ったデータにも保持方針を適用する。保持期間を過ぎた保存回答は、通知の再開前に削除する。復旧によって回答の保持期間を延長しない。
- 復旧点以降に行った個別の削除、メンバーの解除と権限の縮小、トークンの失効は、復旧で元に戻る。CMSはこれらを自動で再適用しない。復旧前に、元に戻る可能性がある操作の種類を運営者へ示し、運営者が必要な操作をやり直す。
- 復旧時に保存済み回答の通知を送信済みか判断できない場合は、送信成功を確認できない失敗として扱い、自動で再送しない。回答が保持されている場合は、運営者が重複送信の可能性を確認して手動で再試行できる。
- 保存基盤全体の喪失では、復旧点以降の受付・回答・編集が失われる可能性と、その期間を示す。復旧できていない受付や移行を成功と扱わない。
- 復旧は設置全体を単位とする。復旧前に、すべてのワークスペースが復旧点へ戻ることと、各ワークスペースで失われる可能性のある期間を確認できる。
- ホスティング運営者が、バックアップの取得と復旧の動作を定期的に確認できる。
- 通知や移行の進行状況、失敗、必要な対処を確認できる。
- 障害や誤操作から復旧するとき、公開内容と未公開内容を区別して扱える。

### 10.3 操作性と分離

- 日常の管理画面は、コンテンツを見つける・編集する・公開する作業を中心に構成する。移行・復元時の問題は該当する操作とコンテンツに結び付けて示す。
- 管理操作の結果、保存状況、エラーの理由を、利用者が理解できる言葉で示す。
- 管理画面の主要な操作をキーボードだけで完了できる。対象はログイン、検索、コンテンツ編集、WYSIWYGの標準編集、メディア選択、項目の並べ替え、保存、プレビュー、公開、回答の閲覧・削除、運用設定の変更とする。
- キーボードのフォーカス位置を視覚的に確認でき、操作順序を理解できる。ダイアログを含め、通常の操作でフォーカスを移動できなくなる状態を作らない。
- 入力項目には支援技術から識別できる名称を付け、必須条件、説明、項目ごとのエラーを関連付ける。エラーを色だけで伝えず、問題のある項目と修正理由を示す。
- 保存結果、入力エラー、処理の完了などの状態変化を、支援技術からも認識できる。
- 日常の編集、公開、受付と、障害時の復旧が各章の保証に従って動作することを検証する。
- 将来のSaaS提供で必要になるワークスペース分離と利用者別のアクセス制御を、セルフホスティングでも維持する。
- 課金や契約管理など、SaaS固有の運営機能は初期版に含めない。

### 10.4 品質の確認

- 通常操作に加え、同時操作、失敗、処理の中断・再開、重複実行、復旧においても、各章の型、公開範囲、アクセス制御、データ保持の保証を満たすことを確認する。
- コンテンツは、下書きの保存と破棄、値の書き換え、公開、公開取り消し、ごみ箱への移動と復元、保持方針による自動整理を経ても、4.2の状態と一意性の規則を満たすことを確認する。値の書き換えが下書きを公開せず、選ばなかった内容と項目を変えないことを確認する。
- フォームは、受付完了の条件、通知の送信失敗の扱い、再試行と宛先の変更、削除と通知の関係を確認する。通知の送信成功を確認できない場合も送信失敗として扱うことを確認する。通知定義が参照する項目を削除する反映が拒否されず、受付と通知が続き、不整合のある参照が通知と管理画面で示されることを確認する。フォームの項目のキーの変更で、変更前のキーへの参照が同じく不整合として示されることを確認する。受付中のフォームを削除する反映で新規受付が終わり、保存済み回答と未送信の通知が残ることを確認する。
- スキーマ変更では、移行定義を順序どおりに適用し、失敗で変更が残らないことを確認する。移行後も、ごみ箱の内容と履歴の版を現行スキーマで復元できることを確認する。キーを変更した項目の値を履歴から戻せ、削除した項目の値が履歴に残らないことを確認する。同じ移行定義の列を異なるワークスペースへ適用し、同じ結果になることを確認する。値の種類の変更が変換規則どおりに変換し、変換できない公開内容があれば失敗することを確認する。フォームとその項目のキーの変更が移行定義なしに削除と追加として反映され、保存済み回答を受付時の定義のまま扱うことを確認する。値の書き換えでごみ箱のコンテンツの値を移せることを確認する。
- コンテンツの構造と移行定義が一致しない反映、適用済みの移行定義を変更した反映、適用済みの移行定義より前に未適用の移行定義を加えた反映、前提の版が反映中に変わった反映、直接反映で現行スキーマが適用済みの移行定義と食い違った状態での移行定義の適用が拒否されることを確認する。直接反映で一致する構造に戻すと、移行定義を適用できることを確認する。
- 初期構成が、データが空の状態の起動でだけ読み込まれ、データがある状態の起動と復旧では読み込まれないことを確認する。初期構成のモデル・フォームごとの運用設定が、そのキーの対象をスキーマの反映で作成したときに紐付くことを確認する。データの保存先を空にして起動し直すと、初期構成とデータ投入で同じ状態から開発を再開できることを確認する。
- 適用の事前確認がデータを変更せず、確認時点のデータで適用した場合と同じ失敗と影響を示すことを確認する。
- CMSに接続しない検証で、コンテンツの構造と移行定義の食い違いを検出できることを確認する。
- スキーマの変更の種類ごとに、6.2の移行を生成し、生成時に判断とデータを失い得る操作を確認して移行定義に記録することを確認する。対応する移行のない変更が削除と追加として生成されることを確認する。
- まとめた移行定義を、まとめる前の列を適用済みのワークスペースで適用済みとして扱い、列の一部だけを適用済みのワークスペースへの反映が拒否されることを確認する。
- 非推奨の対象を編集画面で変更できず、値の書き換えで変更できることを確認する。スキーマの識別子が一致しない要求を拒否せず、不一致を示すことを確認する。画像の派生形式のキーを含む型の形の変更で識別子が変わり、制約・検証・一意性と表示・運用の定義だけの変更で識別子が変わらないことを確認する。モデル・フォームごとの識別子が、ほかの対象の変更で変わらないことを確認する。
- 一括操作の失敗で一部だけが確定せず、メディアを含む公開範囲が意図せず広がらないことを確認する。
- メンバーの解除、権限変更、トークンの失効・期限切れ・入れ替えが各章の条件で反映されることを確認する。ブラウザ用トークンの値が知られても、公開内容の取得とフォーム送信を超える操作ができないことを確認する。メンバーの脱退で公開サイトの表示と受付が止まらないことを確認する。
- 管理検索、キーボード操作、支援技術による入力・エラー・状態変化の認識を確認する。
- 編集の競合、セッションの期限切れ、通信断で、編集者の入力が失われないことを確認する。
- 容量や処理能力の上限で受け付けられない場合は、明確な失敗または送信制限を返す。受付完了条件を満たさない送信や、失敗した移行・復旧を完了と扱わない。
- 本書では、保持件数・同時利用数・処理件数・応答時間の数値目標を定めない。対応環境、利用上限、バックアップ間隔、復旧手順は運用条件として示す。

## 11. 初期版の範囲と達成条件

### 11.1 対象外

- 多言語のコンテンツ管理。
- 予約公開と承認フロー。
- 自由なページレイアウトやデザインの編集。
- 編集を止めないスキーマ移行と、複数世代のスキーマの並行運用。
- CMSと表示アプリの破壊的変更を、準備や保守時間なしで同時に切り替える保証。
- 過去の参照先と表示アプリを含めたページ全体の再現。
- WYSIWYGでの任意HTML・スクリプト・表の直接編集。
- 利用者向けの汎用的なコンテンツのインポート・エクスポート、ワークスペース間のコンテンツの複製、CMSが用意する開発用のテストデータ。CMSは9.3のコンテンツ管理の許可と、10.1の初期構成を提供する。
- CMSによるデータの初期化。データの作り直しは、保存先を空にした起動と10.1の初期構成で行う。
- 設置やワークスペースの用途（開発用・運用中など）による機能の出し分け。
- 管理画面での保存回答の一括エクスポート。

### 11.3 代表サイトでの確認

標準的なコーポレートサイトで、次の利用を一貫して実現できることを確認する。個別の操作手順と検証ケースは設計で定める。

- 会社情報を単一コンテンツ、ニュースとサービス紹介を複数件のモデルとして管理する。
- ニュースをスキーマで定義した公開日の項目で並べ、カテゴリーで絞り込み、総件数を使ってページ分割した一覧と、一意な値による詳細表示を実装する。一覧と詳細で、異なる派生形式の画像を表示する。
- 編集者が本文と画像を編集し、編集画面から下書きのプレビューを開いて確認してから公開する。公開中のニュースを編集して下書きを保存し、公開内容を配信したまま一覧と詳細をプレビューしてから公開する。公開中のニュースを取り消し・削除・復元し、状態と一意な値の扱いを確認する。
- 一般問い合わせとサービス紹介への問い合わせを設け、管理画面で通知メールと返信先を定義する。フォームに項目を追加して反映し、全項目の一覧を使う通知定義を変更せずに受付を続けられることを確認する。通知定義が参照する項目を削除して反映し、受付と通知を続けながら不整合に気付いて修正できることを確認する。通知先の障害で通知が失敗しても受付が完了し、運営者が失敗に気付けることを確認する。誤った通知先を修正してから再試行し、外した宛先へ送られないことを確認する。
- 公開内容、参照先、メディア、スキーマを変更し、公開範囲と下書きを保ちながら表示アプリへ反映する。スキーマの変更は、手元の設置で移行定義を試し、データの保存先を空にして起動し直し、初期構成とデータ投入で同じ状態に戻して書き直してから、運用中のワークスペースで適用の事前確認を行い、表示アプリの切り替えに合わせて適用する。項目の削除を含む変更を、生成時にデータを失い得る操作として確認して適用する。項目のキーの変更と値の種類の変更、スクリプトの値の書き換えによる値の移し替えと非推奨を使った項目の置き換えを含める。値の移し替えで、編集中の下書きを公開しないことを確認する。別のブランチで適用済みの移行定義と食い違う移行定義が拒否され、生成し直してから適用できることを確認する。
- フォームや問い合わせ対象の変更後も、過去の回答と受付済み通知を送信時の意味で扱い、保持方針と通知設定を運用する。フォームの項目のキーを変えた後も、過去の回答を受付時の項目と表示名称で閲覧できることを確認する。
- SSGのビルドとSSRでサーバー用トークンを使い、ブラウザからの絞り込みとフォーム送信にブラウザ用トークンを使う。手元の設置と運用中のワークスペースへ、トークンを切り替えてスキーマを反映する。手元の設置では、初期構成で通知先と送信接続設定を宣言し、起動し直してもそのままフォーム受付を試せることを確認する。サーバー用トークンをブラウザへ渡さないことを確認する。
- プレビュー取得の許可を持つトークンで下書きを取得し、トークンの入れ替えと失効が反映されることを確認する。トークンを発行したメンバーやスキーマを反映したメンバーを解除しても、公開サイトの表示と受付が続くことを確認する。
- 日常の編集・公開・回答確認をキーボードで完了し、バックアップから各章の条件を満たして利用を再開する。
